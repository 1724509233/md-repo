# 回收站（Trash）设计 — P4-4

- 状态：已实现（2026-11-12 验收）；验收后修订 §12 待用户审查
- 日期：2026-11-10
- 关联：todo 164504d3；路线图 P4-4（「先设计稿：deletion 不同步（ADR-0001），回收站 = 服务端 move 语义，影响同步 client 与恢复演练」）；`2026-10-09-webui-file-management-design`（当时回收站为非目标）

## 0 背景与现状

当前删除链路（Web `manage delete` 与 agent `delete_doc` 同构）：

1. `snapshots.capture()` 全文快照（删除类保留 30 天，`/api/memory/rollback` 可回滚）
2. `unlink()` 直接删盘
3. `ledger.record(..., "deleted", ...)` → `apply_change`：files 表删行 + change_log 行 + segments/graph 清理 + **`remove_dead_links` 改写引用方文档内容**（移除指向被删文件的 wikilink）

已知缺口（本设计必须一并解决）：

- **服务端删除 → 客户端复活**：`compare_files`（server/sync.py）只有 `recent_moves`（rename 检测），没有 `recent_deletes`。服务端删文件后，客户端本地副本仍在 → 下轮 sync 判为 `to_push` → 重新上传 → 文件复活。
- 删除不可见、不可恢复（除 30 天快照回滚这一低层机制，无用户面入口）。

## 1 目标 / 非目标

**目标**

1. Web UI 删除（文件/文件夹）= 移入回收站；回收站面板：列表 / 恢复 / 彻底删除 / 清空
2. agent 通道 `delete_doc` 同样移入回收站（语义统一，agent 误删可恢复）
3. sync 修复：被回收站文件在客户端的陈旧副本不再被回推（`recent_deletes`）
4. `.trash/` 在全部索引/扫描/sync 面排除（恢复演练、reconcile、watcher、agent 工具、client 扫描）

**非目标**

- 自动清理（retention 策略）——v1 仅手动清空
- 跨设备回收站同步（回收站只存在于服务端 vault；client 永不拉取 `.trash/`）
- 彻底删除后的引用方内容恢复（link 清理是单向的）

## 2 核心语义：move，不是 delete

| 操作 | 磁盘 | files 表 | segments/graph | 引用方文档内容 | change_log |
|---|---|---|---|---|---|
| 移入回收站 | 文件 → `.trash/<batch>/` | 删行 | 删除 | **不动**（link 暂死） | `deleted` 行（原路径） |
| 恢复 | `.trash/<batch>/` → 原路径 | 建行（`created`） | 重建 | 不动（link 自动复活） | `restore` 行（新增 op，§12.1）+ 引用方 graph 重抽取 |
| 彻底删除 | `.trash` 文件 unlink | （已无行） | （已无） | `remove_dead_links` 清理 | 无新行（删除已在入站时记录） |

**裁决：入站时跳过 `remove_dead_links`**（`apply_change` 新增 kwarg `remove_links: bool = True`，经 `ledger.record` 既有 `**passthrough` 透传，签名不变）。理由：引用方内容不改写 → 恢复完全可逆（link 自动复活）；入站期间指向该文件的 link 显示为死链（UI 已有灰化语义，且是可见的临时态）；彻底删除时才执行 `remove_dead_links`（引用方内容改写触发 watcher 重索引，终态一致）。

外部删除（直接磁盘编辑、未注册写入）不变：文件已不在，watcher 记 `deleted`（source=watchdog），无回收站可言，`remove_dead_links` 照旧。

## 3 存储布局

```
<vault>/.trash/
  20261110T120000Z-a1b2c3d4/        # batch = 一次删除动作（UTC 时间戳 + 8 位 hex，唯一且可排序）
    meta.json                       # {batch, deleted_at, source, files: [{path, size, hash}]}
    notes/a.md                      # 保留原相对路径（文件夹删除 = 一个 batch 含全部内部 .md）
```

- **batch 粒度 = 一次删除动作**：文件删除 = 1 文件；文件夹删除 = 全部内部 `.md`（与现行递归删除同口径）。
- `meta.json` 入站时一次写入、其后不可变（无并发写竞争；`hash` = 删除前内容 SHA-256，供 sync 陈旧判定用）。
- 非 `.md` 文件：与现行一致——不移动、使文件夹存活（系统全链路 `.md`-only）。
- Obsidian 忽略点目录；`.trash` 在 vault 目录内，vault 备份天然包含；**恢复演练不受影响**（index.db 重建扫描排除 `.trash`，见 §7）。

## 4 API

新路由模块 `server/routes/trash.py`（前缀 `/api/trash`，注册进路由表——顺序由 `tests/test_routes_order.py` 钉住）：

| 端点 | 语义 |
|---|---|
| `GET /api/trash` | `{items: [{batch, deleted_at, source, files: [{path, size}]}]}`（扫 `.trash/*/meta.json`，deleted_at 降序） |
| `POST /api/trash` `{action: "restore", batch, path?}` | 恢复整 batch 或单文件；原路径已存在 → 409 |
| `POST /api/trash` `{action: "purge", batch, path?}` | 彻底删除（单文件或整 batch） |
| `POST /api/trash` `{action: "empty"}` | 清空全部 |

**路径校验**：`batch` 对照磁盘 `.trash/` 目录列表验证（不存在 → 404）；`path` 必须是该 batch `meta.json` 的条目（否则 400）。无自由路径输入 → 无 traversal 面。另 `safe_rel_path` 增加首段拒绝 `.trash`（与待办 0eac2e40 的 `.sync` 首段拒绝同批落地）——web upload/download/manage 路由不得直接触碰 `.trash`。

## 5 删除链路改动

### 5.1 Web（`console.py::delete`）

- 文件：capture 快照（**保持不变**）→ 建 batch（mkdir + 写 meta.json）→ `rename` 入站 → `ledger.record(..., "deleted", "web", remove_links=False)`
- 文件夹：同现行口径（`rglob("*.md")`）→ 一个 batch → 逐个 rename 入站 → 空目录清理（dotfiles + rmdir，不变）→ `record_folder` + 逐文件 `record(remove_links=False)`
- **失败语义**：meta 先写、文件后移；部分移动失败 → 已移文件 rename 回原位 + 删 batch 目录 → 500（无半回收站态；比现行「部分删除」更干净，因为 rename 可逆）
- 响应：`{ok, path, deleted_count, batch}`
- **快照裁决：保留 capture（代码不动）**——回收站是主恢复路径，快照是彻底删除后的 30 天兜底，且记忆控制台 rollback 语义不变。代价：入站文件在 30 天内有双份存储（可接受，后续可优化）

### 5.2 agent（`delete_doc`）

- 同 move 语义；`ledger.record(..., "deleted", ctx.write_source, batch_id=ctx.run_id, remove_links=False)`
- 工具描述更新：`"Move a document to the trash (restorable via the trash UI). Not permanent."`（原 "Permanently delete... Irreversible"）
- 快照 capture 保留（不变）；agent 无文件夹删除工具，不涉及

### 5.3 外部删除

不变（§2 末段）。

## 6 Sync（client）

- `/api/sync`：与 `recent_moves` 并列取 `recent_deletes`（`action == "deleted"`，since last_sync，同 200 行窗口）；另扫 `.trash/*/meta.json` 建 `deleted_hashes = {原路径: 删除前 hash}`（trash 小，O(batches)）
- `compare_files(local, server, recent_moves, recent_deletes, deleted_hashes)`：
  - `to_push` 路径 ∈ `recent_deletes`：
    - `deleted_hashes` 有 pre_hash 且本地 hash ≠ pre_hash → **留在 to_push**（用户在服务端删除后本地重建/改写过）
    - 否则（hash 相同，或外部删除无 pre_hash）→ **移入 to_delete**（陈旧副本）
- client `to_delete` 处理逻辑不变（已会删本地文件），日志文案覆盖删除场景
- **窗口限制**：client 离线超过 200 行窗口 → 删除不可见 → 回推（与现行 rename 逻辑同限制，文档化）
- 此修复对**所有**服务端删除生效（含外部删除）——现行「复活」行为改为「跟随删除」。这是修复而非回归，但属行为变更（§11-1）

## 7 索引/扫描排除面（`.trash`）

与既有 `.sync`/`.obsidian` 检查并列新增 `.trash`：

| 位置 | 目的 |
|---|---|
| `snapshot_watcher._norm_rel` | trash 操作不产生 dirty 事件（原路径由 ledger skip 标记处理；`.trash` 路径不得进 ledger → 否则 files 表出现 trash 行） |
| `snapshot_watcher._full_scan` | reconcile 不见 trash 文件 |
| `vault_ops._iter_vault_md` | 恢复演练/全量重建不索引 trash |
| `list_files` 工具 `_index_excluded` | agent 文件列表不含 trash |
| `refs.py` rglob（`update_references_batch` / `remove_dead_links` 同名唯一性检查） | 回收站内同名文件不算「活」重复 |
| `client/sync.py::scan_local_files` | 防御：client 不推 `.trash` |
| 前端 `vaultLinks.js::EXCLUDED_TOP` | 防御 |

**不入 `EXCLUDED_INDEX_DIRS`**：该集合语义 = 机器区（files 表行仍维护）；`.trash` 永远无 files 表行，语义不同。

## 11 风险与开放问题

1. **复活修复是行为变更**：现行「服务端删除 → 客户端回推复活」改为「客户端跟随删除」。属修复，但需用户确认——尤其「服务端删除后用户在本地重建同名文件」场景：内容 hash 与删除前相同 → 判陈旧删除；不同 → 正常推送。
2. **200 行窗口**：client 长期离线 → 删除不可见 → 回推（与现行 rename 同限制）。
3. **快照冗余**：入站文件 30 天内有 `.trash` + 快照 blob 双份。裁决保留（彻底删除后兜底 + 记忆控制台 rollback 语义不变），后续可优化。
4. **恢复时引用方 graph 重抽取**：O(vault) 内容扫描（`_find_referrers` 全扫回退）——恢复是低频用户动作，可接受。
5. **0eac2e40 依赖**：`safe_rel_path` 的 `.sync` 首段拒绝是未落地 bug；本设计同批加 `.trash` 拒绝（可同 commit，或 `.trash` 先行）。
6. **记忆控制台 rollback 与回收站并存**：若用户经记忆控制台回滚了一个已入站删除，文件重现而回收站仍有副本 → 回收站恢复该条目时 409（路径已存在），文案提示即可。

## 12 验收后修订（2026-11-12，用户裁决）

### 12.1 change_log op：恢复记 `restore`（第 5 个 canonical op），arm 不包含 restore

**裁决**：入站记 `delete`（语义可接受，不变）；恢复原记 `created` → **改记 `restore`**（恢复的文件 ≠ 新文件，create 语义不符）。`log_change` 为 passthrough 归一化（`_ACTION_TO_OP` 未收录的 action 原样落库），但 `change_log` 表 DDL 有 `CHECK(op IN 4-set)` 约束会拒绝 restore 行——**需 schema 扩展**：CHECK 扩为 5-set（DDL 抽为 `_CHANGE_LOG_DDL` 单一来源，fresh CREATE 与迁移重建共用）+ 幂等迁移 `_ensure_change_log_restore_op`（旧库检测存储 DDL 无 'restore' → 单事务 rename→create→copy→drop→reindex，**保留行**——sync 200 行窗口与 UI 变更流不重置；`init_db` 连接为 autocommit（`isolation_level=None`），无外层事务，`BEGIN IMMEDIATE` 安全；在 file_changes 合并与 batch_id 迁移之后调用）。

**arm 不包含 restore（用户裁决）**：`TRIGGER_OPS` 不收录 `restore`（config 层 `trigger.events` 无法表达 restore arm）；`_has_human_activity_since` 的 `ops=("create",)` 不加。恢复不 arm 后台 agent。**行为变更（有意）**：现行恢复伪装成 op=create，会 arm events 含 create 的 agent；改后不再 arm。

落点：

1. `trash.py::restore`：`ledger.record(..., "created", ...)` → `"restore"`
2. `server/vault/db/schema.py`：`_CHANGE_LOG_DDL`（5-set CHECK，单一来源）+ `_ensure_change_log_restore_op` 幂等迁移 + `init_db` 接线（见上段）
3. `file_ops.py::apply_change`：created 分支元组加 `"restore"`（upsert + index_segments + graph_extract_file 同分支）；`_invalidate_wikilink_filename` 条件（现 `("created", "create")`）加 `"restore"`——文件名重新出现，trash 期间若 wikilink 缓存了「同名解析到别的文件」，不失效会持续返回旧结果（功能性，非仅标签）
4. `app.js` pollChanges 的 treeChanged 列表（现 `['created','deleted','moved']`）加 `'restore'`——否则另一台设备恢复文件时本机文件树不刷新（功能性回归风险）
5. bgagent：`TRIGGER_OPS` / `_has_human_activity_since` / 各 agent `trigger.events` **均不加** restore（见上裁决）
6. `test_trash.py::test_restore_whole_batch` op 断言 `"create"` → `"restore"`；新增回归：恢复后 `count_changes_sources(conn, ops=("create",))` 不计 restore 行（arm 不含 restore 钉住）；`test_db.py` 新增迁移测试（旧 4-op 库 → 行保留、索引重建、restore 可插入、重跑幂等）
7. AGENTS.md trash 条目（「created 行」→「restore 行」）+ 本 spec §2 表

不受影响（已验证）：sync 只筛 deleted/moved（restore 行照旧被忽略，仍占 200 行窗口一行）；`recent_changes` 工具 passthrough（LLM 直接看到 "restore"，自解释）；MonitorPage 渲染 raw op；reminders op 无关；files 表同分支 upsert。

### 12.2 Bug 1：回收站面板「清空」按钮死功能

- **症状**：点击「清空」无任何 API 调用、无 console error。
- **根因**：`TrashPanel.js` 模板的清空按钮（L126-132）漏绑 `@click`——`onEmptyClick`（两步确认：首击变红「确认清空？」、3s 内再击执行）已在 setup 定义并 return，但模板从未接线。
- **批量清空 API 已存在**：`POST /api/trash {action:"empty"}` → `trash.empty()`（purge 全部 batch），测试已覆盖（`test_empty_purges_all` / `test_api_trash_purge_and_empty`）→ **无需新增 API**。
- **修复**：按钮补 `@click="onEmptyClick()"`（一行）。

### 12.3 Bug 2：打开的文档移入回收站后，chat 仍传陈旧 doc_path → 409

- **机制**：`AIChatPanel::doSend` 恒带 `doc_path: props.docPath`（= `state.currentPath || ''`）；服务端 `/api/agent/chat` 预检（`agent.py` L130-137）：doc_path 非空 + 过 `safe_rel_path` + 盘上不存在 → **409** `doc_path '...' not on disk`。
- **状态缓存** = `state.currentPath`（当前打开文档）。现有三处重置逻辑全部用**路径精确匹配**：
  1. `manage('delete')` → `_applyChangeToCurrentDoc`（web FileTree 删除）
  2. `handleToolResult` delete_doc 分支（agent SSE 快路径，2026-10 409 回归修复）
  3. `pollChanges` → `_applyChangeToCurrentDoc`（跨设备 / SSE 断连兜底）
- **确认的缺口：文件夹删除**——当前文档位于被删文件夹内时 `c.path === state.currentPath` 不成立（文件夹路径 ≠ 文档路径）→ `currentPath` 不清 → chat 传陈旧 doc_path → 409。三处共用同一精确匹配逻辑，**同缺口**。单文件删除路径在代码中已有清除（若实测复现为单文件场景，修复阶段按此缺口同策覆盖即可——修复对两种场景统一生效）。
