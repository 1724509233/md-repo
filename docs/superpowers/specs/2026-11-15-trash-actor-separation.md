# Trash 与 actor 分离：删除恢复机制全文

> 源出 AGENTS.md Gotchas「Trash + actor separation」条，2026-11-20 AGENTS 瘦身原文迁出，此处为唯一完整机制记录；AGENTS 只留铁律句。约束定稿 2026-11-15（P4-4），pre_hash 契约定稿 spec 2026-11-15 §2。

Deletion recovery is split by actor — the **workbench** (web console + interactive agent, `write_source` = `web`/`agent`) deletes via `move_to_trash` with **no snapshot capture** (recovery = the trash UI; expiry = 30-day purge); the **non-workbench** (bgagent alias + mcp, `write_source` = alias/`mcp`) deletes via **direct unlink + full pre-image snapshot** with **no trash** (recovery = the rollback UI, block ⑦; expiry = 30-day GC). The branch criterion inside `delete_doc` is `ctx.write_source == "agent"`; a bgagent alias of `agent` is rejected at config load (it would misroute deletions to the trash). Trash mechanics: batch = UTC `YYYYMMDDTHHMMSSZ-<8hex>`; files keep their original relative path; `meta.json` = `{batch, deleted_at, source, files:[{path,size,hash}]}` — written first at inbound, immutable after. Inbound = `move_to_trash` (meta first, files after; partial failure → moved files renamed back + batch dir removed — never a half-trash state) + `ledger.record(..., "deleted", source, remove_links=False, pre_hash=<pre-delete SHA-256>)` — referrer content is NOT rewritten (the link is temporarily dead; restore is fully reversible). Restore = rename back + `restore` row + referrer graph re-extraction (inbound's `graph_delete_file` already removed the referrer→target edges, so referrer lookup = edges lookup first, O(vault) content-scan fallback — design §11-4). Purge/empty = unlink trash copy + `remove_dead_links` on the original path (the deferred content cleanup for workbench deletions; liveness-checked) + drop the batch; **no new change_log row** (the deletion was booked at inbound). Routes: `GET /api/trash` (list) + `POST /api/trash` `{action: restore|purge|empty, batch?, path?}` — batch validated against the on-disk `.trash/` dir list (404), `path` must be a meta entry (400), original path exists → 409. `.trash` is excluded from every index/scan surface (watcher `_norm_rel`/`full_scan`, `_iter_vault_md`, `list_files`, refs rglobs, `_resolve_wikilink`, `_find_referrers`, degraded rag fallback (`ai/search.py _legacy_rag_search`), agent `_check_md_path`/policy first segment) — a new scan surface must add the `".trash" in parts` check the same way. **pre_hash** (change_log column, spec 2026-11-15 §2): every deletion entry point books the pre-delete SHA-256 at the deletion point; the sync lane derives `deleted_hashes` = `{原路径: pre_hash}` from `change_log` delete rows (latest row per path wins, **unbounded** — change_log is persistent; replaced `trash.deleted_hash_map` and plugs the snapshot-side resurrection hole: bgagent/mcp deletions never enter the trash, so a trash-derived map would let a client push a stale copy back). `compare_files` rules: a `to_push` path with an entry in `deleted_hashes` → **to_delete** (stale copy, prevents resurrection) UNLESS the entry is a pre-hash AND the local hash differs (user recreated/rewrote after the deletion → stays `to_push`) or the path is still alive on the server (2026-11-17 review M1: `p in server` skips the gate entirely — a live file is not a stale copy of any historical delete; delete→recreate closes that path's past, so a client restoring the exact pre-delete content at a recreated path is not deleted); `""` entries (external deletions, no pre-hash) are always stale. The map keys are move-chain-resolved original paths (a client-held pre-move copy of a moved-then-deleted file is still caught); a move→edit→delete chain leaves the client's pre-move copy in to_push (hash evidence insufficient — documented residual blind spot); likewise a recreate+re-delete at a vacated alias path keeps the alias's hash — the recreated content's own deletion is not mapped (same blind-spot family). Move rule runs first and wins if both claim a path. Client `scan_local_files` excludes `.trash` like `.sync`; `to_delete` log says "renamed or deleted on server". **Link cleanup is split too**: trash purge cleans workbench deletions, GC expiry (snapshots.py `gc`, expiry-boundary block) cleans snapshot deletions — both call `remove_dead_links`, which is liveness-checked (target on disk → 0 files touched; a recreated file never loses its referrers' links); GC derives its path set from change_log (`op='delete' AND ts < cutoff AND source NOT IN ('web', 'agent')`, newest first, LIMIT 1000 — the source filter keeps not-yet-purged trash batches' referrer link text intact: trash restore is content-reversible, stripped link text cannot be re-extracted; external deletions (watchdog, no recovery channel) ARE GC's cleanup) and caps actual cleanups per sweep at `GC_DEADLINK_CAP=5` (gc_after_capture fires on every capture). Block ⑦ (rollback-calls UI) shows delete-class snapshots = only non-workbench deletions (bgagent/mcp) after the separation.
