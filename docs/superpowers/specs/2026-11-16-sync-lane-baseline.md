# Sync lane：基线三分法与删除门 机制全文

> 源出 AGENTS.md Gotchas「Sync lane」条，2026-11-20 AGENTS 瘦身原文迁出，此处为唯一完整机制记录；AGENTS 只留铁律句。评审 F1–F4 定稿 2026-11-16，C1 修正 2026-11-17。

`/api/sync` does three-way classification against the client's uploaded baseline (`baseline_files`, optional — absent/malformed = legacy conflict behavior): in-both hash-diff with `local == baseline` → server-modified → `to_pull`; `server == baseline` → client-modified → `to_push`; neither → conflict. The deletion gate replays ALL change_log move/delete rows (seq ASC, unbounded — not gated by `last_sync` or the 200-row window) via `derive_deleted_hashes` into `{original path: pre_hash}`, resolving move chains (a client-held pre-move copy of a moved-then-deleted file is still caught); `recent_deletes` is gone from the route, `recent_moves` keeps its window. Cold rebuilds re-seed delete rows via `recovery.seed_deleted_prehashes` (trash meta + ledger snapshots; rename/move history is an accepted loss, as are external `watchdog` deletes — their `""` sentinel rows lived only in the wiped index.db, so a stale local copy of an externally-deleted file can resurrect after a cold rebuild — and so are already-purged trash batches + snapshot rows GC'd past 30 days: both seed sources are exhausted, those deletions cannot be re-seeded). The client sends `baseline_files` from its saved `state["files"]` — which keeps only server-AGREED hashes, picked per path in three tiers (2026-11-17 independent-review C1 fix): ① agreed this cycle — a successful pull books the pulled bytes' hash, a successful push the actually-uploaded bytes' hash (NEVER the closing rescan hash: the file may be edited again after the op); ② untouched since the top-of-cycle scan (rescan hash == scan hash) — the rescan hash IS the agreed content; ③ everything else (conflicted / failed push / guard-rescued / edited mid-cycle) keeps its previous entry, or drops out if it never had one, so the next cycle re-flags it instead of silently pull-overwriting the local edit. Tier order is load-bearing: the non-agreed guard must outrank the untouched check (the conflict loop never touches the conflicted local file, so its rescan == scan — checked the other way round, C1 revives through the conflict entrance). The client guards BOTH directions of the cycle: a pulled file edited mid-cycle (disk hash ≠ reported hash) gets the server copy saved as a conflict file instead of being overwritten, and a `to_delete` path edited mid-cycle is skipped — not unlinked; the next cycle re-classifies (genuine rewrite → `to_push`, still-stale copy → deleted then — except external-delete `""` entries, which have no pre-hash to compare against and are always deleted, per the always-stale rule).
