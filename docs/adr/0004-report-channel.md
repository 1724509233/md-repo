# 报告通道：非提案角色的机器区直写

bgagent 角色分两类：有落地动词的提案角色（固化者）与无落地动词的报告角色（哨兵 / 叙事者）。v2.1 的 §7.2 把「propose = bgagent 唯一写入口」定为整表口径，但报告角色的产出（只读报告）既不走提案终审（无落地动词、无可合并内容），v1 的落点 `weekly/`（用户区）又在 v2 宪法下违宪（用户区对自动化写路径字节级零写）。2026-10-27 grill 会话拍板：**设立「报告通道」**——无落地动词角色 = 读工具 + `write_doc`（写边界 = 机器区 `index/`），无 propose、不写用户区；提案角色无直写。

## Considered Options

- **B（否决）：报告 = 账本 DB 行，无文件，控制台 API 读库。** 表面理由是与 D25（提案零文件落）同构。否决理由：(1) D25 的逻辑不迁移——提案的本质是状态机，v1 文件 + DB 是同一状态的两份拷贝（双行问题根源）；报告没有状态，文件是唯一源，不存在冗余拷贝可杀。(2) 工具负担：主 agent 参与终审 / 引用报告时需要新读工具访问 DB 行；文件方案用既有 `read_doc`（`index/` 可读、不进搜索图谱）零新增。(3) 判例冲突：errata 卡与报告是同一类东西（LLM 独一产出、无状态机、人面 = 控制台），errata 已定为机器区文件 + 控制台 API——报告走 DB 行会开出同一类东西两套介质模式的先例。(4) 文件方案的免费项：快照强制开（LLM 独一产出）、导出 / 离线读 / 未来 VCS 全部免费；DB 行需自造版本化故事。
- **C（否决）：保留 `weekly/`（用户区）作为 v0.1 例外。** 与 D4 的精确化（「自动化写路径绝对化，不记例外；人执笔写路径不是例外，是另一类写入」）直接抵触。

## Consequences

- 机器区写者面从「唯一执行器 + 提案机制」扩为三者，报告通道是第三个——spec §二 表、§7.2 工具面表、§九 修正案 1 同步修订（落点见 v2.2 grill 记录 §三）。
- **分界线是承重的**：直写通道专属非提案角色；提案角色（固化者）= propose 唯一写入口、无直写。若某角色同时持 propose 与 write_doc 且目标含机器区，终审闸门（summary / errata 的人确认）可被直写绕过——config 校验应拒绝该组合（v2a 债单 #7 的范围）。
- 报告 = LLM 独一产出，快照强制开（rollback 语义分区表已覆盖「报告」）；`write_doc` 既有捕捉 / `register_write` 管线免费覆盖。
- 哨兵 / 叙事者 `target_dir` 从 `suggestions` / `weekly` 迁至 `index/`（config 迁移，债单 #8）；`weekly/` 退役。
- **bgagent 产出漂移叠加**（重复 run 的产出重叠 / 叠加去重）明示为范围外、未来优化方向（grill Q10 用户原话）——报告通道打开后这是最可能先冒头的债。
- 人面声明随本 ADR 钉死：Web UI 控制台 = 唯一设计人面，Obsidian 不在设计目标内（连带修正 §三.1「Obsidian 版本历史兜底」等 v1 时代残留前提）。
