信息架构 · 为什么是流水
  • 时间 = 免费的优先级——倒序排列让「刚发生的」永远在顶部，新提案到达即置顶（脉冲给最新一条，与现组件口径一致）；不再需要「审查队列」和「历史」两个分区各占一屏。30 秒扫描 = 看账目条两行 + 流顶 1-2 个事件。
  • 账目条 sticky——九态（9 计数，零态淡显 / awaiting 铜 / failed 红）+ 触发（agents.armed / config arm_count）+ 召回（failed_7d / docs_tracked）压成两行，position:sticky 钉在滚动区顶：翻多深的流水，扫描层都不丢。这是 v3「脉搏」的替代：从区块变成层。
  • 三类信息进流——提案 = 卡（awaiting 可点进详情 / 终态淡显带落地或理由）；后台任务 = 细行标记（agents.last_run 相对时刻 + 触发进度，不占卡的高度）；历史状态 = 终态卡 + 卡内 trail（场景 02）。平铺的四个区块被拆进同一条时间线，各自保留原字段。
  • 排序口径——流内按事件时刻倒序（created / last_run / merged_at / ts）；跨天用日分组小标（今天 / 昨天 / 10-18）。深链（通知 → 具体提案）仍直达终审详情，不经过流。
  • 样式取向——报刊年鉴节奏：衬线标题 + mono 时间轴（32px 左列 + 1px 竖线 + 节点点），纵向留白比 v3 松一档；铜只给「需要我」（awaiting 节点 / 最新到达），终态一律淡显。

痕迹层 · 终态卡怎么写
  • 历史状态 = 终态卡——merged / rejected / failed 的提案在流上保持原位（按状态翻转时刻），淡显（opacity .82）+ 状态 pill + 一行附注：merged 给落地文件 + merged_at，rejected 给 reject_reason，failed 给执行器失败原因。翻流水 = 翻决策史，不需要单独的「历史状态」区块。
  • 轨迹随卡——merged 卡内嵌 2 行 trail（/proposals/{relpath}/trail：seq · source · op · path，human → executor 闭环可见）。完整 12 条 tail 仍在详情面，流上只给最近 2 行。
  • failed 不淡进背景——pill 红色（唯一非铜强调），因为 failed = 需要人留意（snippet 待修 / 状态待重试）；其余终态一律灰调。
  • 账目条不变——翻到任何深度，顶部两行仍是当前全局态（Await 3 / 触发 c 2/3 / 召回 3·42）：流水看「过程」，账目条看「现状」，两层分工明确。
  • 深度与加载——演示流到 10-18 为止，尾行「按需加载」示意；生产实现 = 按 created 倒序分页（/api/memory/proposals 全量返回后前端切片即可，轮询 30s 天然刷新）。

  • 账目条回行——本帧演示九态 mono 9px 在 390px 下的自然回行（九态一行折成两行，触发/召回行保持一行）；position:sticky 钉顶不变，30 秒扫描层在移动端仍然成立。若实测回行 >3 行挡住流顶，生产降级 = 只留六核心态（await / adopt / merged / reject / failed / process）+「其他 +N」，九态全集留给详情面。
