方案 B · 账本行式（密度维度）
  • 差异 = 只动容器，不动内容——卡片容器（背景 / 圆角 / 阴影 / 内边距）全部去掉；「行」成为最小单元：每区块 = 一行 mono 行头（区块名 + 右对齐计数/状态词）+ 内容行，行距 4px，区块间靠 1px 细线分隔。mono 占比拉高，视觉从「设置页」变「对账单」。内容、顺序、口径与稿 D 一致。
  • 选择它的理由——监控页的主访问 = 快速扫一眼「有没有坏」：行头右对齐的状态词让六个答案排成一条纵向扫描线，同屏信息量三方案最大，无卡片间隙浪费；对经常开的工程师友好，像看一份系统对账单。
  • 代价——①「设置页气质」丢失：行距 4px 的 mono 墙对不常开的用户有压迫感，首访认知成本高；②区块视觉边界弱，「卡感」没了之后异常清单等需要被看见的区块只能靠红字，视觉锚点少；③内部行盒（tr-row / rev-row）去圆角降边后，层级全靠缩进和细线，细节对比度低。
  • 零态落点——区块计数 = 0 → 行头状态词淡显（.bh-r.z）+ 内容行 = 淡显占位（.zline），不省略区块（演示数据全非零，稿中不实例化）。
  • L2 入口——无卡片头可挂，改为召回内容行末尾的 mono 文字按钮（▾ L2 深钻），展开机制同稿 A 0fr→1fr，不产生 a11y 隐面。

  • 选择它的理由——监控页的次要访问 = 「大概看一眼，有问题再点」：六行 = 六个答案的目录，认知负载最低；异常默认展开保证红字可见，不牺牲告警。
  • 代价——① 默认信息量三方案最低（数字在行上，细节要点）；② 六行全是按钮 = 页面「全交互」，扫读时点击目标被高估（不知道哪些值得点）；③ 展开后页变长，无锚点回跳，多区块同开时要滚动管理；④ 九态 3×3 藏在体里，「一眼九格」没了。

  • 口径注（本稿专门写明）——30s 轮询 = 快照，无时序数据：只画静态比例条 / 刻度条，不画动画填充、不画趋势曲线（轮询间隔 30s 的「增长」是假象，趋势图会误导「在改善/在恶化」）；状态灯脉冲 = armed 在跑（状态不是时序，可保留）。归一化副作用：值域窄时差异被压缩（61 vs 42 的条长差 = 22 个百分比点，视觉上已近），条尾 mono 数值兜底。
  • 最近终态 = 唯一不换内芯的区块（本稿判断）——终态 = 事件非比例：「10-20 merged」没有刻度可画，强行图形化只会产出无信息装饰；事件流的语言就是文字行。
  • 选择它的理由——比例、开/关、多少是监控的原生语义，图形的扫读压缩 > 文字：刻度条一眼 2/3，比「arm 2/3」再快一档；卡片骨架保留 = 设置页气质不丢，异常红边在卡堆里天然跳出；对非工程师（看「有没有坏」）最友好。
  • 代价——① 图形信息密度低于 mono 文字：「上次 26m 前 / 今天 1/3 次」图形放不下，仍走注脚行，图形只表达一半；② top5 比例条把 last_hit 降为副注、path 在 200px 列截断，三字段变两行；③ 新图形组件（.seg / .lamp / .wbar）= 新 DOM + 动画 + 归一化口径，维护成本三方案最高；④ 同屏信息量仍不及 B（图形省字数但不省行数，六区块高度不变）。
  • 零态落点——卡片常驻，内容行 = 淡显占位（.zline），同 B；sentinel arm 0/10 的 10 段全空刻度条 = demo 数据自带的零态图形样本（不需要造数据）。
