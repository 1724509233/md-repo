信息架构 · 为什么是账本
  • 平铺 → 层级——v3 在一屏里平铺「队列 + 九格 + 触发条 + 召回块」四种密度不同的内容；稿 A 改为四条账目行，行头只承担「一眼数」：3 件待审 / 2 个 agent / merged 5 · rejected 2 / 在轨 42。展开才付出注意力成本，grid-template-rows 0fr→1fr 折叠（复用产品已有模式）。
  • 扫描路径 = 行头，行动入口 = 行 01——「30 秒扫完」只看 4 个汇总数 + 尾行九态；要动手时才展开 01 进队列。后台任务 / 召回 / 历史是监控信息，默认收起不打断「逐条审」的主线。
  • 异常自述——汇总数的次行 s 位直接说异常：「7d 无命中 3」「failed 1」「adopted 1 待落地」。30 秒判断不需要展开任何行，展开只是要明细。
  • 九态压缩——3×3 九格占 3 行高度，改为账本尾行的一行式计数（两行 wrap），零态淡显、awaiting 铜色、failed 红。信息量不丢，垂直占用减半。
  • rail 徽标仍 = awaiting_review 队列长度（topbar 铃铛同理，deep-link 直达终审详情，场景 03）。

钻取内容 · 各行放什么
  • 行 01 队列——卡片规格沿用 v3（类型 chip + 标题 + 年龄 / 来源路径 + run_id），source_refs[0] 与 run_id 由 /api/memory/proposals 富化（status 队列只有 5 字段，与现组件同口径）；脉冲铜点只给最新一条，选中卡高亮，点入场景 03。
  • 行 02 后台任务——trigger_state：满足条数 / arm_count（端点 armed_target 恒 null，目标值取 config：consolidator 3、sentinel 10）+ 进度条 + last_run + 今日 runs_today / 预算（config：3 / 2）。执行器 30min 循环单列一行注脚（armed 口径 = 有 adopted 未落地或 14d 超期提案）。
  • 行 03 历史状态——四终态单元格（adopted 待落地 / merged 已落地 / rejected / expired）。取舍：落地文件路径按单条聚合，端点无「全局最近落地」字段，不编造；指向详情 trail 兜底。
  • 行 04 召回——三统计 + top3 路径（recall.top：path + weighted，failed_7d / docs_tracked）；「高召回」定义 tip 沿用 0fr→1fr 点击展开。
  • 演示脚本——行头点击切换 .open（0fr→1fr 过渡）；召回 tip 点击展开；不调真实 API。生产接线 = 组件 watch 同一份 30s 轮询数据，行头汇总数是 by_status / agents / recall 的纯函数。
