信息架构 · 为什么拆两列
  • 痛点定位——v3 队列面 = 队列 + 九格 + 触发条 + 召回块平铺；「30 秒扫描 + 逐条审」的用户其实只用队列，其余是监控。本稿按使用目的拆面：审给行动、脉给监控，分段控件切换，默认审。
  • 审列的减法——九格 3×3 压成一行式计数（九态不丢，垂直占用减半）；召回块压成一行数字，留「详情 →」入口切脉列（本场景可点，切面动画 = 现有 opacity + 8px 位移 口径）。队列独占版面，3 张卡不必滚动，扫描与审查同屏。
  • rail 徽标 / 深链——徽标 = awaiting_review 长度，点入 = 审列（行动面）；通知深链指向具体提案时直接进终审详情（场景 03），不经过审列列表。
  • 空队列稳态——审列空态 = 结论句 + 九态一行 + 召回一行仍在（系统活着的证据不离开行动面）；要细看监控就切脉列。

脉列 · 监控面放什么、怎么写
  • 九态一行垫底——两个面共享同一行式九态（审列在底部、脉列在顶部），扫描时无论在哪一面都看得到全生命周期计数；awaiting 铜、failed 红、零态淡显。
  • 后台任务——trigger_state 两行：满足条数 / arm_count（端点 armed_target 恒 null，目标值取 config：consolidator 3、sentinel 10）+ 3px 铜进度条 + last_run + 今日 runs_today / 日预算（config：3 / 2）。执行器是确定性 30min 循环（无 trigger 武装），单列虚线行： armed 口径 = 存在 adopted 未落地或 14d 超期提案。
  • 召回——三统计（failed_7d / docs_tracked / top 加权和）+ recall.top top3 路径（path + weighted，last_hit 可作 tooltip）；「高召回」定义 tip 沿用 0fr→1fr 点击展开。
  • 最近终审——历史状态的可读渲染：取 /proposals 中非 awaiting 的最近终态（merged / rejected 各一例），给出状态 pill + 落地路径或 reject_reason。单条完整轨迹仍在详情（trail），此处只回答「系统最近做过什么判断」。
  • 样式取向——脉列 mono 主导、密排（分区 padding 10px vs 审列 12px）、无衬线标签：与审列的衬线卡片语言区分「机械看 / 人来审」。整面只读，无动作行。

详情面 · 稿 B 的处理
  • 五段材料照单保留——类型+状态+标题+年龄 / 内容摘录 / 来源（可跳转）/ 批次·可逆 / 相似记忆比对，顺序 = 判断顺序。稿 B 与现版完全同构，差异只在头栏多了分段控件：审完这条可以不动位置直接切脉列扫一眼再回来，动作行与切面互不打断（sticky 底不变）。
  • 位次「1/3」——当前提案在 awaiting_review（oldest first）中的位次，与审列卡片序一致。
  • 动作行 sticky——采纳铜实心主操作；驳回展开必填理由（非空可提交，服务端 400 同口径）。成功后出现确认之后：状态翻转 + merged_at + 落地文件 + trail（seq · source · op · path；executor 行未落地前虚线「下一循环」——API 只移状态，执行器才落文件，spec 铁律）。
  • 深链口径——通知 / 铃铛深链指向非 awaiting 提案时同样落在本面「确认之后」子视图（与现组件一致），分段控件停在审侧。
