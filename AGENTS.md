# AGENTS.md

## agent-browser CDP (Windows)

Verified 2026-10-13 with agent-browser 0.39.0 on Windows:

- `agent-browser --cdp <port>` works fine when a Chrome is already listening on that port (`open`, `snapshot`, `click "@eN"`, `read`, `tab list` all OK).
- **Never run `agent-browser --cdp <port> close`** on an externally launched Chrome — it kills the external Chrome process tree. To stop, kill Chrome directly (`Stop-Process`).
- If no browser is listening on the CDP port, commands fail with a misleading `Operation timed out. The page may still be loading...` and can leave a hung `agent-browser-win32-x64.exe` process. Before retrying: check the port with `netstat -ano | findstr :<port>` and clean up leftover `agent-browser*` processes.
- To launch a CDP Chrome manually: `& "<chrome.exe>" --remote-debugging-port=9222 --user-data-dir="<dir>" about:blank` (run in background).

## Architecture

- **server/** — FastAPI app. `api.py` has the `create_app(vault_dir, db_conn, ledger_conn, ai_config, bg_targets)` factory (wiring only); routes live in `server/routes/` (one module per URL-prefix domain: console/notifications/sync/recall/memory/agent), each registering via `register(app, ctx)` on the `WebContext` (exposed at `app.state.ctx`). Route-table order is pinned by `tests/test_routes_order.py`. `main.py` is the entry point that wires config → db → app → `build_runtime()` (named runtime assembly: event bus + publisher filters, the four ledger callbacks, snapshot watcher, bgagent tasks; returns a `Runtime` with `stop()`) → uvicorn.
- **server/vault/** — Index subsystem, split into submodules: `db/` (SQLite schema, conn, file_index, segments_sql, fts_query, graph_sql, changes, sessions, recall, relatedness, trigger_state, notifications, proposal_records, snapshot_records), `fs/` (segmenter, link_parser, vault_ops), `orchestration/` (indexer, move_detect, refs, file_ops). Import directly from the real modules (e.g. `from server.vault.db.file_index import get_all_files`) — the `service.py` facade is gone (card 5).
- **server/agent/** — LLM agent system: `agent.py` (Agent class), `runtime.py` (LoopRuntime streaming loop), `session.py` (SessionManager), `tools/` (15 tools, one module each: read_doc / search_docs / list_files / get_related_docs / recent_changes / recall_stats / propose / list_proposals / get_proposal auto; write_doc / edit_doc / delete_doc / move_docs / adopt_proposal / reject_proposal ask), `policy.py` (channel policy), `prompts.py`, `reminders.py`.
- **server/bgagent/** — Background agents with independent model configs: `scheduler.py` (cron + event arming), `runner.py` (run_once), `notify.py` (in-app notifications), `executor.py` (framework role, not an LLM agent).
- **client/** — Python polling client. `sync.py` has `scan_local_files()`, `sync_once()`, `run_polling_loop()`. `main.py` is the entry point.
- **tests/** — pytest suite. `conftest.py` provides `vault_dir`, `db_conn` (index domain), `ledger_conn` (ledger domain, 2026-10-31 split), `app`, `client`, `ai_config` fixtures.

The vault directory is both the data store and the Obsidian vault. `.sync/` inside it holds **two SQLite files** (2026-10-31 ledger-file split, L4): `index.db` (rebuildable cache — files/segments/change_log/…; freely rebuildable, see `recovery.py`) and `ledger.db` (authoritative, not rebuildable — proposals/proposal_transitions/snapshots/relatedness; **the recovery drill only ever touches index.db**). Backing up the system must include **both** files. First-boot migration of the four tables from index.db → ledger.db is in-path (`migrate_ledger`, idempotent, per-machine); `logs/` also lives in `.sync/`.

## Gotchas

- **Windows newline translation**: test fixtures write sample files in binary mode (`write_bytes`) so SHA-256 hashes match. If you add test fixtures with text files, use `write_bytes` not `write_text`, or hashes will differ on Windows.
- **移动端键盘与视口（2026-11-17 华为 Mate60 双内核复盘，详见 `issues/2026-11-17-mobile-keyboard-viewport-shift.md`）**: 应用壳高度必须走 `html,body,#app{height:100%}` 链（Tailwind `h-full`）——`h-screen/100vh` 壳在「键盘压布局视口」型内核（Edge/安卓）下不随键盘收缩，overflow-hidden 文档仍会被 scrollIntoView 程序化滚走（顶部被遮、触摸不可恢复；fixed 抽屉不受文档滚动影响，「只有主区偏」即此指纹）。所有会弹键盘的聚焦调用必须 `focus({preventScroll:true})`（防「只压可视视口」型内核平移 visualViewport，原生浏览器复现过）。安卓 Chromium 无 iOS 式 <16px 自动缩放，勿按 iOS 思路修。回归钉：`test_shell_uses_layout_viewport_height` + `test_keyboard_focus_preventscroll`。
- **锚点激活行为（2026-11-17 bug 4a2249fc 返工复盘，详见 `issues/2026-11-17-tree-anchor-activation-jump.md`）**: 文件树文件行是 `<a href="#doc/…">`（P1-4 深链），行内交互元素（rename input、⋯ 按钮）的 click 只写 `@click.stop` 仍会跳文档——点击链接后代元素照样激活祖先 `<a>` 默认行为（hash 变 → hashchange → openDoc），该旁路不经任何 Vue handler。必须 `@click.stop.prevent`。泛化红线：任何有默认行为的容器（`<a href>`/submit 按钮/label）内的交互子元素都要 `.prevent`；跳转/滚动类 bug 先按层列监听全集（Vue handler / 原生默认 action / window 级 hashchange-scroll）再看触发元素在每层之上还是之下。回归钉：`test_rename_row_click_guard`（双层断言，单层放行过半成品修复）。
- **Sync lock is a cross-process file lock**: a `SyncLock` instance (`server/core/sync_lock.py`) constructed by `create_app` and exposed at `app.state.ctx.sync_lock`. It claims `<vault_dir>/.sync/sync.lock` via atomic `os.open(O_CREAT|O_EXCL)` (stdlib only — no fcntl/msvcrt), so two server processes on the same vault (e.g. 9888 dev + 9889 feature-test) cannot sync concurrently; the file is removed on release. The file content is the acquire timestamp (+ pid); a lock older than 300s is stale and take-over-able (a crashed sync must not wedge the vault), unreadable/empty content is treated as stale (fail-open). The `locked_at` in-memory attribute is checked first and remains the test seam: tests that need to simulate a locked state set it directly (see `test_sync_lock` in `tests/test_api.py`) — a refusal at the seam never touches the filesystem. Constructed without a lock path, `SyncLock` is pure in-memory (unit-test mode).
- **Path traversal guard**: `safe_rel_path()` in `server/vault/fs/vault_ops.py` (aliased `_safe_rel_path` in the route modules) rejects paths with `..` or leading `/` (checked on the backslash-normalized form — UNC/extended-length shapes included), any drive-qualified start (`^[A-Za-z]:`; on win32 a pathlib join with a drive-qualified argument discards or swaps the vault base), and a first segment of `.trash`/`.sync` (system dirs are unreachable via the web routes — upload/download/manage must never touch them; the `.sync` half is bug 0eac2e40). Deeper same-named dirs are user content.
- **Deletion is not synced**: if a client deletes a file, it simply won't appear in `local_files`. The server keeps it. On next sync it shows up in `to_pull` (server has it, client doesn't). This is by design.
- **Conflict files**: saved as `{stem}.conflict-{device_name}{suffix}` (e.g. `notes/test.conflict-mac.md`). The local version is kept untouched.
- **Config**: both server and client read a single `config.yaml` with both `server:` and `client:` sections. Each side only reads its own section. Copy `config.example.yaml` to `config.yaml` and edit.
- **First-run indexing**: `ensure_indexed` (server/vault/orchestration/indexer.py) is a two-level check: ① segments content table empty → full rebuild of segments + graph; ② `segments_fts_docsize` row count ≠ segments row count → FTS-only rebuild (re-reads the content table, does not touch disk). `count(*) FROM segments_fts` cannot detect desync (on an external-content table it scans the content table). Not DB emptiness — the old `_self_heal` pattern is gone.
- **No auth, no HTTPS**: LAN-only by design. Don't add authentication unless the spec changes. Exception (2026-11-17 user decision): the MCP write channel authenticates the stdio process via MD_VAULT_MCP_WRITE_TOKEN matching config.yaml mcp.write_token (constant-time compare); unauthenticated MCP stays read-only + propose. LAN HTTP surface remains auth-free.
- **`server.vault` root imports are deprecated**: the shim in `server/vault/__init__.py` emits a DeprecationWarning and re-exports the 38 legacy names directly from the real modules (the `service.py` facade was deleted in card 5; the shim surface is pinned by `tests/test_vault_shim.py`). The shim will be removed in a future release. Tests still import through it — don't break them.
- **Change ledger (server/ledger.py)**: the sole write surface for `change_log` + `files`. Agent write tools (write/edit/delete/move) call `ledger.record(...)` synchronously AFTER the write — the row (files + change_log) must land before the `tool_result` SSE reaches the UI, whose fast-path `loadDocs()` reads the `files` table (regression 2026-11-04: async `register` left a ~1.6s window → stale tree; vault issue `agent-write-file-tree-stale`); the skip mark makes the later watcher event book nothing (exactly one row per write). Other in-process channels (executor, bgagent runner, web upload/save) call `ledger.register(path, source[, batch_id])` BEFORE writing — the watcher consumer (`ledger.consume`, the four `on_*` callbacks in main.py's `build_runtime`) books exactly one correctly-attributed row. Web direct writes (manage_docs, where the console feed must respond instantly) call `ledger.record(...)` — synchronous row, consumer books nothing. Folder rows go through `ledger.record_folder(...)` (the watcher has no folder callbacks — no double-row risk). `apply_change` / `apply_folder_change` (file_ops.py) are the row mutators: **no module other than ledger imports them**; the only in-module caller is `reconcile` (offline startup, no watcher running). Unregistered writes (external processes such as MCP stdio, direct disk edits) fall back to `source="watchdog"` on the consumer side — that is the consumer's fallback, not a writer exception. op strings are normalized to the canonical 4-set by `_ACTION_TO_OP` at the `log_change` entry — do not "fix" op vocabulary in callers.
- **Background agents**: configured under `background_agents:` in config.yaml. Each has independent cron, model config, target_dir scope, and prompt file. Alias must be unique; target_dirs must not overlap.
- **Sync lane (2026-11-16, review F1–F4)**: `/api/sync` does three-way classification against the client's uploaded baseline (`baseline_files`, optional — absent/malformed = legacy conflict behavior): in-both hash-diff with `local == baseline` → server-modified → `to_pull`; `server == baseline` → client-modified → `to_push`; neither → conflict. The deletion gate replays ALL change_log move/delete rows (seq ASC, unbounded — not gated by `last_sync` or the 200-row window) via `derive_deleted_hashes` into `{original path: pre_hash}`, resolving move chains (a client-held pre-move copy of a moved-then-deleted file is still caught); `recent_deletes` is gone from the route, `recent_moves` keeps its window. Cold rebuilds re-seed delete rows via `recovery.seed_deleted_prehashes` (trash meta + ledger snapshots; rename/move history is an accepted loss, as are external `watchdog` deletes — their `""` sentinel rows lived only in the wiped index.db, so a stale local copy of an externally-deleted file can resurrect after a cold rebuild — and so are already-purged trash batches + snapshot rows GC'd past 30 days: both seed sources are exhausted, those deletions cannot be re-seeded). The client sends `baseline_files` from its saved `state["files"]` — which keeps only server-AGREED hashes, picked per path in three tiers (2026-11-17 independent-review C1 fix): ① agreed this cycle — a successful pull books the pulled bytes' hash, a successful push the actually-uploaded bytes' hash (NEVER the closing rescan hash: the file may be edited again after the op); ② untouched since the top-of-cycle scan (rescan hash == scan hash) — the rescan hash IS the agreed content; ③ everything else (conflicted / failed push / guard-rescued / edited mid-cycle) keeps its previous entry, or drops out if it never had one, so the next cycle re-flags it instead of silently pull-overwriting the local edit. Tier order is load-bearing: the non-agreed guard must outrank the untouched check (the conflict loop never touches the conflicted local file, so its rescan == scan — checked the other way round, C1 revives through the conflict entrance). The client guards BOTH directions of the cycle: a pulled file edited mid-cycle (disk hash ≠ reported hash) gets the server copy saved as a conflict file instead of being overwritten, and a `to_delete` path edited mid-cycle is skipped — not unlinked; the next cycle re-classifies (genuine rewrite → `to_push`, still-stale copy → deleted then — except external-delete `""` entries, which have no pre-hash to compare against and are always deleted, per the always-stale rule).
- **Trash (server/vault/orchestration/trash.py, P4-4) + actor separation (2026-11-15)**: Deletion recovery is split by actor — the **workbench** (web console + interactive agent, `write_source` = `web`/`agent`) deletes via `move_to_trash` with **no snapshot capture** (recovery = the trash UI; expiry = 30-day purge); the **non-workbench** (bgagent alias + mcp, `write_source` = alias/`mcp`) deletes via **direct unlink + full pre-image snapshot** with **no trash** (recovery = the rollback UI, block ⑦; expiry = 30-day GC). The branch criterion inside `delete_doc` is `ctx.write_source == "agent"`; a bgagent alias of `agent` is rejected at config load (it would misroute deletions to the trash). Trash mechanics: batch = UTC `YYYYMMDDTHHMMSSZ-<8hex>`; files keep their original relative path; `meta.json` = `{batch, deleted_at, source, files:[{path,size,hash}]}` — written first at inbound, immutable after. Inbound = `move_to_trash` (meta first, files after; partial failure → moved files renamed back + batch dir removed — never a half-trash state) + `ledger.record(..., "deleted", source, remove_links=False, pre_hash=<pre-delete SHA-256>)` — referrer content is NOT rewritten (the link is temporarily dead; restore is fully reversible). Restore = rename back + `restore` row + referrer graph re-extraction (inbound's `graph_delete_file` already removed the referrer→target edges, so referrer lookup = edges lookup first, O(vault) content-scan fallback — design §11-4). Purge/empty = unlink trash copy + `remove_dead_links` on the original path (the deferred content cleanup for workbench deletions; liveness-checked) + drop the batch; **no new change_log row** (the deletion was booked at inbound). Routes: `GET /api/trash` (list) + `POST /api/trash` `{action: restore|purge|empty, batch?, path?}` — batch validated against the on-disk `.trash/` dir list (404), `path` must be a meta entry (400), original path exists → 409. `.trash` is excluded from every index/scan surface (watcher `_norm_rel`/`_full_scan`, `_iter_vault_md`, `list_files`, refs rglobs, `_resolve_wikilink`, `_find_referrers`, degraded rag fallback (`ai/search.py _legacy_rag_search`), agent `_check_md_path`/policy first segment) — a new scan surface must add the `".trash" in parts` check the same way. **pre_hash** (change_log column, spec 2026-11-15 §2): every deletion entry point books the pre-delete SHA-256 at the deletion point; the sync lane derives `deleted_hashes` = `{原路径: pre_hash}` from `change_log` delete rows (latest row per path wins, **unbounded** — change_log is persistent; replaced `trash.deleted_hash_map` and plugs the snapshot-side resurrection hole: bgagent/mcp deletions never enter the trash, so a trash-derived map would let a client push a stale copy back). `compare_files` rules: a `to_push` path with an entry in `deleted_hashes` → **to_delete** (stale copy, prevents resurrection) UNLESS the entry is a pre-hash AND the local hash differs (user recreated/rewrote after the deletion → stays `to_push`) or the path is still alive on the server (2026-11-17 review M1: `p in server` skips the gate entirely — a live file is not a stale copy of any historical delete; delete→recreate closes that path's past, so a client restoring the exact pre-delete content at a recreated path is not deleted); `""` entries (external deletions, no pre-hash) are always stale. The map keys are move-chain-resolved original paths (a client-held pre-move copy of a moved-then-deleted file is still caught); a move→edit→delete chain leaves the client's pre-move copy in to_push (hash evidence insufficient — documented residual blind spot); likewise a recreate+re-delete at a vacated alias path keeps the alias's hash — the recreated content's own deletion is not mapped (same blind-spot family). Move rule runs first and wins if both claim a path. Client `scan_local_files` excludes `.trash` like `.sync`; `to_delete` log says "renamed or deleted on server". **Link cleanup is split too**: trash purge cleans workbench deletions, GC expiry (snapshots.py `gc`, expiry-boundary block) cleans snapshot deletions — both call `remove_dead_links`, which is liveness-checked (target on disk → 0 files touched; a recreated file never loses its referrers' links); GC derives its path set from change_log (`op='delete' AND ts < cutoff AND source NOT IN ('web', 'agent')`, newest first, LIMIT 1000 — the source filter keeps not-yet-purged trash batches' referrer link text intact: trash restore is content-reversible, stripped link text cannot be re-extracted; external deletions (watchdog, no recovery channel) ARE GC's cleanup) and caps actual cleanups per sweep at `GC_DEADLINK_CAP=5` (gc_after_capture fires on every capture). Block ⑦ (rollback-calls UI) shows delete-class snapshots = only non-workbench deletions (bgagent/mcp) after the separation.

## 安全与隐私红线（2026-11-18 外部 MCP 通道评审定稿，常驻约束）

背景定性：本系统的安全当前依赖**事实性前提**（LAN≈可信、MCP stdio=本机进程、LLM 端点可指本地）——事实会随功能演进破裂，下列红线约束一切破裂前提的改动；核心哲学一句话：**把隐式信任显式化为契约**（提案通道、人审闸门、actor 信任戳、写 token 全是同一哲学的切面，新维度按此推演，不引入新哲学）。

1. **信任边界必须从事实走向契约**：把 stdio/LAN 信任面开放给网络或多租户前（HTTP transport、远程端点、设备接入），先立显式契约——设备配对、per-device credential、可吊销面。无鉴权的新暴露面 = 红线违例，功能再小也不行。
2. **禁止单点加固**：给任何面加鉴权/隔离前，先对照系统整体水位（Web 面是刻意无鉴权的，见 Gotchas「No auth」条）。不允许造出「上了锁的门挨着没门的门」的错觉；整体安全水位的迁移是用户的显式决策，不是单功能的副产品。
3. **身份由通道背书（trusted stamp）**：`actor` / `run_id` / `write_source` 一律由通道入口代码注入，永不来自模型或请求参数。任何新传输面（尤其多租户）必须**从连接凭证在服务端解出身份再注入**——trusted stamp 在传输层破功 = 全部归因与审计失效。
4. **prompt 不是安全机制**：隐私/注入边界只在工具层做成硬过滤时才存在。内容进入模型上下文的瞬间即已成事实（出域/污染），系统提示词里的行为约束（如「不要复述敏感内容」）不得作为任何保护手段写进设计。
5. **索引层也是数据，隔离必须三点齐全**：任何读取/隐私隔离必须同时覆盖 policy 读边界、读工具、索引面（FTS 摘要片段、relatedness 边、recall 台账）——缺一即筛子。注意现状：**读边界今天是刻意全库**（`ChannelPolicy` 只约束 ask 工具，reads stay unrestricted），敏感分区是 0→1 施工图，不是给现有机制打补丁。
6. **默认保守，放开显式**：网络监听默认 localhost（开 LAN 须配置显式声明并写明后果）；写通道默认关（`mcp.write_token` 空=关闭是范式，新凭证一律同构）。
7. **出域必须可知**：任何把 vault 内容送往域外端点（云端 `base_url`，含内置 AI 与 bgagent）的通道要有台账行（仿 recall 的 source 模式）+ 云端端点启动/首用提示。事实性前提破裂必须是**可见事件**，不是静默事实。
8. **快照是兜底不是第一道防线**：snapshots 每路径仅保留最近一份 pre-image（被取代行即时 GC，`snapshot_records.gc_sweep`）——「反正能回滚」不得作为放行危险写入的前提；不可逆写（mass overwrite、机器区槽覆盖、无人工闸门的 auto 轨）要人工闸门或配额/限流，不是事后回滚。

已核实的现状缺口（做相关功能时先对照，勿当已解决）：外部 MCP 无提案状态回查；change_log 对外部写归因退化为 watchdog；auto 轨（entity_index/relatedness）免鉴权可入机器区且 source_refs 不验存在性；长驻 MCP 进程在主服务器未运行时检索看不到自己的写入。

## Frontend UI Workflow

Web UI is a Vue 3 CDN SPA (no build step): `server/templates/index.html` is the shell that loads `app.js`, with component modules under `server/templates/js/` (`components/` + `utils/`) plus `style.css`. Static assets are served via `/static` (mounted from the templates directory in `api.py`). Tailwind CSS Play CDN + Flowbite 2.5.2.

### Rules

1. **Design-first**: For any UI layout change (panel placement, responsive behavior, animation, scroll strategy), present the approach to the user BEFORE implementing. Do not iterate reactively — decide placement, transition mechanism, and content reflow strategy upfront.
2. **Copy norms** (2026-11-04, 监控页移动端评审后定稿): UI 只放用户做判断/行动需要的信息——状态、数量、时间、标题；实现 meta（后端字段名、端点路径、L2/trigger_state 这类设计概念）不进正文。刷新节奏只表达一次（页头「更新于 HH:mm」），卡头不重复。统计口径的解释进 title tooltip 或 L2 详情层，不写常驻小字。
3. **Verify before commit**: UI/CSS changes require user visual confirmation in a browser before committing. "Tests pass" ≠ "UI works". Never commit layout changes without explicit user approval.
4. **Segmented writing**: HTML files >100 lines must be written in segments (structure → styles → scripts), not one-shot. This makes diffs reviewable and errors locatable.
5. **Panel/drawer checklist**: Before implementing any slide-in panel or drawer, explicitly decide:
   - Placement: side (left/right) vs bottom vs overlay
   - Transition: `transform` (GPU, no reflow) vs `width`/`flex-basis` (triggers reflow) — prefer transform
   - Content reflow: does the main content area resize? If yes, how does centering/scrolling behave?
   - Toggle control: where is the button? Must be visible in BOTH open and closed states. Position must not jump between states.
   - Z-index layering: does the toggle get occluded by the panel? Use `position: relative; z-index` if needed.

### Known Pitfalls (learned the hard way)

- `position: absolute` panels don't participate in flex layout — main content width doesn't change, so `mx-auto` centering is visually off. Fix: add `padding-right` to main area when panel opens.
- `min-h-[Xpx]` on content children prevents the container from shrinking when a panel takes space.
- `flex-basis` transitions cause content reflow (text rewrapping) during animation. Use `transform: translateX()` instead for GPU-accelerated, zero-reflow slides.
- Scroll position is not preserved when container height changes during a transition. If this matters, anchor an element and adjust `scrollTop` per frame via `requestAnimationFrame`.
- Tailwind Play CDN generates styles at runtime — class names in JS `classList.add()` work, but dynamically constructed class strings must be complete (no partial matching).
